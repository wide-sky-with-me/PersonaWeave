# 决策笔记（Agent Notes）

`docs/` 写“系统现在怎样运转”，这里写“当初为什么这样做、否定过什么”。笔记服务将来的维护者和新开的 Agent，防止他们把已被否定的方案当成新想法再提一遍。治理规则见 [documentation-governance.md](../../docs/documentation-governance.md)。

## 什么时候写

只在“非平凡改动”时写：改变默认值、模型/供应商选择、状态机、存储或失败语义、安全边界，或排查出一个会再次踩的坑，或明确拒绝了一个看起来合理的方案。改样式、修单文件 bug、重命名不写。

## 放哪里、叫什么

`.agents/notes/<领域>/<YYYYMMDD>-<短横线标题>.md`。领域目录：`swap`、`refinement`、`windows`、`frontend`、`platform`，缺则新建。**不维护全局索引**（避免多分支并行时合并冲突），靠目录和文件名检索。

## 必备结构

```
# 标题（一句话写出结论）
状态：有效 | 被 <相对路径> 取代
日期：YYYY-MM-DD

## 背景
## 决策
## 被放弃的方案
## 影响与验证
```

- **被放弃的方案**最重要：写清当时还想过什么、为什么不选；缺了它，下个会话很可能重新提议。
- **影响与验证**只链接代码、配置、测试或可复现的记录；不手抄接口列表。
- 一篇笔记只讲一个决策，正文建议 80 行以内。

## 只增不改

旧结论不原地改写。方案变化时新增一篇，在新笔记写“取代 <旧笔记>”，旧笔记仅把“状态”行改为“被 … 取代”。事实性变化改 `docs/`，不要回改历史笔记。

## 与测试的分工

测试保证当前代码行为；笔记保证未来的 Agent 记得为什么。二者不重复：能被测试断言的事实写进测试，不写进笔记。
