# 任务历史是服务端状态的只读投影，工程恢复必须显式

状态：有效
日期：2026-10-04

## 背景

批任务历史、精修会话历史和可编辑的 Studio 工程长期并存。列表曾面临传输图片载荷、浏览器状态与服务端状态不一致、查看历史时覆盖当前编辑输入这三类风险。原先写在 `task-history.md` 的“工程原则”是这些取舍的结论，这里补上被否定的做法。

## 决策

- 列表用轻量摘要，详情在打开单个任务时才取；服务端持久化状态是事实源，浏览器存储只做可选补充。
- 结果提交的当下就保存后续复核需要的不可变原图和产物，缺失时明确返回不可用。
- 只读历史与可变的编辑器恢复隔离：查看历史不写 `useStudioStore`，恢复工程是显式动作。
- 兼容行为必须显式声明，旧记录不靠猜测迁移；测试覆盖载荷边界，不只覆盖顺利渲染。

## 被放弃的方案

- **复用重量级详情对象做列表**：列表成本随图片数线性增长，还会把请求体、URL 和 base64 带进历史页。
- **以浏览器 `localStorage` 为准或让它覆盖服务端状态**：换设备、清缓存就会得出与事实不符的状态。
- **查看历史时顺手把旧任务的源图、映射、遮罩写回编辑器**：悄悄覆盖用户正在编辑的输入。
- **缺失文件时重建替代结果、或为旧记录猜测人脸序号/素材**：会把无法证明的内容显示成成功。
- **事后补存原图**：任务或文件被清理后无法还原，所以必须在提交结果时保存。
