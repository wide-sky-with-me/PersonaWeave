# 保留发布入口并按真实职责提取领域边界

状态：有效
日期：2026-10-14

## 背景

组织审查指出导航护栏、导入检查和前端查询键的问题，并列出流水线、批任务、会话存储及跨聚合协作的结构项。维护者要求在新分支完成处理、全部测试后推送，Mac 部署保持不变。现有源码入口、安装包、便携构建和公开链接共同依赖顶层 api/core/utils 与 docs/wiki 路径；换目录本身没有可验证的业务收益。

## 决策

保留顶层包、CLI、公开文档文件名、数据库 schema 和接口路径。用安装入口护栏及实际 wheel 构建验证兼容，不增加一套 src 布局兼容转发树。

把单脸对齐、遮罩、校色及回贴归到 [face_execution](../../../core/face_execution.py)，[pipeline](../../../core/pipeline.py)仍负责模型缓存/锁、检测、人物分配和逐脸连续编排；原单脸方法及实际引用的分块合成导入入口保留。实际人物来源枚举、已分配结果和跳过原因归到现有 [task provenance](../../../api/tasks/provenance.py)，精修接续和工程恢复共享，不引入事件总线。

[SessionArtifacts](../../../api/refinement/artifacts.py)持有内容寻址、完整性和受控磁盘 I/O；[store](../../../api/refinement/store.py)保留 SQLite 归属、revision/幂等、事件以及接受/取消/删除/恢复事务。服务实际调用的快照/读取方法继续由 store 提供；延迟证据读取仍校验数据库归属。制品助手自身不是访问控制入口，事务回滚和发布归属由 store 决定。

## 被放弃的方案

- 整体移动到 src、迁移 docs/wiki 后留转发：增加安装、便携、公开链接与历史引用的兼容负担，并不改善领域耦合；本次以真实职责提取和安装验证处理结构问题。
- 按行数拆开批任务或 SQLite 状态机：会分散取消、恢复、失败及提交顺序。只提取稳定计算/来源规则和独立文件 I/O，连续状态机保留。
- 通用 repository 或事件总线：现有调用关系不足以证明其价值；增加包装及隐含恢复顺序，反而弱化现有显式编排。
- 让底层制品 helper 直接替代 store：磁盘存在不等于数据库归属，会破坏接受与延迟证据读取的授权边界。

## 影响与验证

既有调用方和发布路径稳定，内部规则不再反向依赖精修编排。仍是一应用进程负责恢复，进程内锁不是分布式租约；原子发布依赖同文件系统，暂存删除不是跨进程崩溃原子擦除。源码分支交付不等于已升级运行实例。
