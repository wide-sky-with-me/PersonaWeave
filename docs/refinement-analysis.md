# Refinement evidence, diagnosis and prompt boundary

The analysis half of a refinement turn: what the model sees, how people are bound to identities, what a diagnosis may say, and how untrusted text is bounded. Session and status semantics are in [ai-refinement.md](ai-refinement.md); generation and review in [refinement-generation.md](refinement-generation.md); the prompt version and official sources in [refinement-prompts.md](refinement-prompts.md). Code: `core/refinement/conversation.py`, `contracts.py`, `prompts.py`, `evidence.py`.

## Evidence roles

- `ORIGINAL` anchors pose, people count, composition, scene and occlusion relationships, **not** the intended facial identity: a requested face replacement is not automatically an error.
- `CURRENT` is the complete selected image to assess and, if authorized, edit.
- `REFERENCE_BOARD_PERSON_N` is the desired identity evidence of stable `person_id=N`. A board holds only that person's references, is labeled with the same ID at the top and on every tile, and fits whole reference images without detection or cropping. List position, board arrival order or a fresh left-to-right face ordering never reassign IDs; missing references stay explicit.
- Review adds `BEFORE` (the explicitly selected input revision) and `CANDIDATE`, so it sees original + before + candidate + the same boards. Boards are never sent to the generator.

The creation snapshot names each original detection's fixed left-to-right face index and, when original dimensions are known, its face-center percentages. These text locators keep stable person IDs distinct from image-specific indices and never re-detect or reorder candidates; missing dimensions omit coordinates. Existing sessions keep their frozen locators and can be clarified through discussion.

Evidence images precede the final text query. Full photo evidence (original, current, before, candidate) is a JPEG overview with a maximum edge of 3200 pixels (`VISION_MAX_SIDE` in the conversation service); smaller inputs keep their dimensions. That is an application budget, not a provider capability claim: provider-side sampling can still restrict detail or reject a request, which must fail explicitly instead of silently dropping someone's evidence. Reference boards keep their own layout: at most 24 people and eight references per person, a 320×352 tile per reference, up to two columns. Decoded arrays must be nonempty uint8 BGR within the shared pixel bound, and the cumulative decoded-evidence budget in [refinement-session-api.md](refinement-session-api.md) applies.

## Diagnosis

`analyze(original, current, people, references, history, user_message, *, previous_diagnosis=None) -> Diagnosis` calls `AIGateway.structured_vision_completion` with `vision_alias("refinement")` and makes one structured response with text repair disabled (see [refinement-generation.md](refinement-generation.md#errors-and-retries)). It never generates or accepts, whatever the user or image text says; the backend controls the mode.

The model jointly considers identity appearance, anatomy, occlusion, blending, lighting, texture and composition. The `Diagnosis` fields (messages, `issues[]`, `people[]`, `edit_plan`, uncertainties) are defined in `core/refinement/contracts.py`. These rules shape them:

- Issue categories are exactly `identity`, `anatomy`, `occlusion`, `blending`, `lighting`, `texture`, `composition`; there are no numeric scores. Region, description, evidence and suggestion need at least 3/12/12/8 characters, and low confidence needs an uncertainty explanation. Extra fields such as tool calls, scores or acceptance decisions are rejected.
- `identity_status` is `match`, `mismatch`, `uncertain` or `unavailable`. Missing references require `unavailable` with an explanation; occlusion, incompatible viewpoints, tiny faces or ambiguous locations may require `uncertain`. These are visual comparisons, not verified identities. `mapping_confident` is about correspondence to a supplied person and is separate from visual similarity.
- Cross-field rules in the initial JSON schema (they do not relax validation or enable repairs): unavailable/uncertain identity needs a nonempty uncertainty explanation; `mapping_uncertain` is the OR of uncertain person mappings; `needs_edit` and `edit_plan.changes/instructions` agree; assessment IDs are exact and unique. Missing, extra or duplicate IDs and identity claims without references are rejected; a valid schema is not proof of visual accuracy.
- The prompt never assumes a defect and has no score threshold. A clean image returns `needs_edit=false`, `issues=[]`, `edit_plan.changes=[]`; small faces, profiles, occlusion or too few comparable features yield uncertain, not invented anatomy or identity. A concrete user-requested whole-image change justifies a plan without a fabricated defect, and user requirements stay separate from model observations. `needs_edit` is advice, not authorization to pay for a generation. Ambiguous person mapping requires clarification before generation.
- The summary is 1–3 short sentences without repeating structured issues. Natural profile perspective is distinguished from visible anatomy problems; glasses, hands and small objects crossing a face are checked against original scene evidence; hidden features are never invented and uncertain evidence never becomes a confident instruction. These are prompt requirements, not a guarantee of model behavior.

The server supplies the explicitly confirmed diagnosis (or, for direct API commands without a binding, the latest completed diagnosis) of this exact base as structured `previous_diagnosis`, outside truncated prose history, and core validates its schema and person bindings before the call. The prompt treats earlier findings as untrusted hypotheses to recheck, merges supported observations with human feedback, lets current visual preferences override conflicting earlier suggestions, explains omitted or corrected suggestions and asks for clarification when ambiguity remains. The plan restates reference observations as self-contained visual instructions because the generator cannot see the references; discussion notices stay in `assistant_message` rather than contradicting an actionable plan. Generation receives the plan, issues and the original current user message; issues are evidence, not a second mandatory checklist. Tests: `tests/test_refinement_conversation.py`, and exact-base selection in `tests/test_refinement_sessions.py`.

## Untrusted data and bounded context

Images (including OCR), person descriptions, earlier assistant prose and user text are untrusted task data. User text may ask for a visual change but cannot alter system roles, tool permissions, credentials, execution mode or publication policy. Variable content is JSON-encoded in an escaped data envelope and never interpolated into the system instruction; the full trusted JSON schema accompanies the initial call. Only the most recent eight history entries count, only user/assistant string content is kept, at most 2,000 characters per entry and 12,000 in total; system/tool history and image-bearing message objects are not replayed. Current messages over 4,000 characters and person locators over 300 characters are rejected before any model call instead of truncated; these budgets and the 24-person maximum live once in `core/refinement/contracts.py`, shared by API and core. Only historical context is truncated. These measures define authority and bound inputs; they do not claim a prompt alone resists adversarial text. Hard enforcement comes from separate methods, the absence of tools, typed schemas and how generation input is built.
